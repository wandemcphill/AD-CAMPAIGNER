# Deployment

FlipTrybe Ads Campaigner is prepared for Render Blueprints from the repository root.

## Render resources

The `render.yaml` blueprint provisions:

- `fliptrybe-api`: NestJS API web service with `/v1/health` checks.
- `fliptrybe-web`: customer dashboard.
- `fliptrybe-admin`: operations dashboard.
- `fliptrybe-worker`: BullMQ worker.
- `fliptrybe-postgres`: managed PostgreSQL database.
- `fliptrybe-redis`: Render Key Value instance for Redis-compatible queues.

The API service runs Prisma migrations in `preDeployCommand` before starting.

## GitHub to Render flow

1. Push this repository to GitHub.
2. In Render, create a new Blueprint from the GitHub repo.
3. Render will detect `render.yaml` at the repo root.
4. Confirm the generated services, database, and Key Value instance.
5. Add any real provider secrets when prompted. Leaving them blank keeps Phase 1 on mock adapters.
6. Deploy the Blueprint.

## Production notes

- `JWT_SECRET` and `SESSION_SECRET` are generated by Render.
- Provider integrations default to `mock` until real credentials are added.
- `DATABASE_URL` is injected from Render Postgres.
- `REDIS_URL` is injected from Render Key Value.
- The Key Value instance is internal-only with `ipAllowList: []`.
- Service names are used for the expected `onrender.com` URLs; update `APP_URL`, `ADMIN_URL`, `API_URL`, and `NEXT_PUBLIC_API_URL` if Render assigns different subdomains.
